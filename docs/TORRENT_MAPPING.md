# Torrent mapping กลาง (schema 2 — การย้ายข้อมูลระยะแรก)

`torrent_store.MappingStore` เป็นชั้นกลางสำหรับอ่านและบันทึกข้อมูล โดยคงรูปแบบเดิมของ
รายการ `torrents`, หลักฐานแหล่งที่มา, ทะเบียนโซน, ตำแหน่งบนโหนด และความสัมพันธ์
Cross-Seed ไว้ ใน schema 2 จะเพิ่มข้อมูลรายการของแต่ละเว็บไซต์เข้าไปในฐานกลาง
เพื่อให้ส่วนของโปรแกรมที่ใช้โครงสร้างเดิมยังทำงานต่อได้

```json
{
  "schema_version": 2,
  "torrents": [],
  "site_zone_registry": [],
  "site_records": {
    "BEARBIT:123": {
      "site": "BEARBIT",
      "torrent_id": "123",
      "infohash": null,
      "legacy_state": {"hash": "UNKNOWN", "hr": true},
      "obligations": {
        "hr": {
          "status": "required",
          "checked_at": null,
          "expires_at": null,
          "verification_method": "legacy_protection"
        }
      }
    }
  },
  "site_sync": {},
  "clients": {},
  "migrations": {},
  "upload_jobs": {},
  "content_groups": {}
}
```

`legacy_state` เป็นข้อมูลในรูปแบบที่ตัวอ่าน H&R/Quest เดิมใช้งานได้ โดยเก็บอยู่ใน
mapping กลาง ส่วน `infohash` ใช้เชื่อมรายการบนเว็บไซต์เข้ากับรายการ torrent
หากยังหา hash ของรายการบนเว็บไม่ได้ ระบบจะเก็บรายการนั้นไว้และคงการป้องกันไว้
จนกว่าจะยืนยัน hash ได้ การย้ายข้อมูลจะไม่เดาแหล่งที่มาหรือสรุปว่าเนื้อหาเหมือนกัน
และ torrent หนึ่งรายการสามารถเชื่อมกับหลายรายการบนเว็บไซต์และหลายตำแหน่งบนโหนดได้

## การบันทึกและย้ายข้อมูล

เมื่อเริ่มโปรแกรม `initialize_mapping()` จะนำเข้าข้อมูลจาก `db/*_link_db.json`
ทุกไฟล์เพียงครั้งเดียว โดยเก็บไฟล์เดิมไว้ และสำรอง mapping เป็น
`torrent_mapping.json.pre-central.bak` ก่อนแปลงข้อมูลครั้งแรก หากพบไฟล์ผิดรูปแบบ
hash ของรายการบนเว็บขัดแย้งกัน หรือ schema รุ่นใหม่กว่าที่รองรับ ระบบจะหยุดการย้ายข้อมูล
ห้ามตีความไฟล์ที่เสียหายว่าเป็นฐานข้อมูลว่าง

หลังย้ายข้อมูลแล้ว `load_db`, `save_db` และฟังก์ชัน async ที่ครอบการทำงานเหล่านี้
จะอ่าน–เขียนผ่าน `site_records` ใน mapping กลาง การแก้ไฟล์ DB เดิมจะไม่มีผลต่อ
สถานะที่โปรแกรมใช้งานอีกต่อไป ตัวอ่านแต่ละระบบจะรวมเฉพาะการเปลี่ยนแปลงในขอบเขตของตน
เพื่อไม่ให้การบันทึก H&R เขียนทับฟิลด์ของ Quest และการย้ายข้อมูลจะไม่ทำให้สถานะ
`clear` เก่ากลายเป็นหลักฐานที่เพิ่งตรวจสอบ

ทุกส่วนที่เขียนข้อมูลต้องใช้ `MappingStore.update()` หรือถือ `transaction()`
ไว้ตลอดขั้นตอนอ่าน–แก้ไข–บันทึก ส่วน `mapping_transaction()` ในโปรแกรมหลัก
รองรับการเรียกซ้อนจาก async task เดียวกัน และใช้ lock ระหว่างโปรเซสตัวเดียวกัน
การอ่านไม่ต้องถือ lock เพราะการเขียนใช้ `fsync` และแทนที่ไฟล์แบบ atomic
ห้าม `await` การอัปเดตผ่าน store ขณะถือ mapping transaction ของโปรแกรมหลักอยู่แล้ว
เพราะการอัปเดตนั้นจะพยายามขอ lock เดิมอีกครั้ง ให้ใช้ `save_mapping` ภายใน
transaction นั้นแทน

ไฟล์ `.lock` ที่อยู่ข้าง mapping ใช้ประสานการเขียนข้อมูล ห้ามลบขณะที่ยังมีโปรเซส
เขียนข้อมูลอยู่ ระบบปฏิบัติการจะคืน lock เมื่อโปรเซสสิ้นสุด การจัดเก็บแบบ JSON นี้
รองรับระบบไฟล์ภายในเครื่อง ยังไม่รองรับระบบไฟล์เครือข่ายหรือการเขียนจากหลายเครื่อง
API ของชั้นจัดเก็บเป็นจุดสำหรับเปลี่ยนไปใช้ SQLite ในอนาคต

## ยืนยัน Source Zone จาก Cross-Seed

Cross-Seed ที่ผ่านการตรวจ manifest ตรงกัน, inventory ที่โหลดครบ และ tracker ของ candidate
สามารถยืนยัน `Source Zone` ผ่าน `site_listings` ได้ โดยผูกกับ infohash ของ listing นั้นเท่านั้น
ถ้า candidate เป็นคนละ hash จะนำหลักฐานไปใช้กับเรกคอร์ดของ candidate เมื่อมีอยู่
และไม่ย้ายโซนของ candidate ไปให้ hash ต้นทาง แม้ใช้ไฟล์ชุดเดียวกัน

เมื่อมีหลักฐานเว็บ/โซน/ID ที่ตรงกันเพียงชุดเดียว ระบบเติม `source_site`, `source_zone_id`,
flags ที่ยืนยันแล้ว และ `source_zone_evidence.verification_method=cross_seed_verified_listing`
พร้อม hash, listing ID/URL, เวลา และหลักฐานการตรวจ
ระบบตรวจทะเบียนเว็บ/โซนที่เปิดไว้ URL แบบสาธารณะ และ hash ใหม่ทุกครั้งที่ใช้หลักฐานนี้
ข้อมูลต้นทางและโซนที่ยืนยันไว้เดิมจะถูกเก็บไว้เมื่อมีหลักฐานใหม่ขัดแย้งกัน
หลักฐานหลายเว็บ หลายโซน หรือหลาย listing ID ที่ยังเลือกไม่ได้จะคงสถานะเดิม

รายการเก่าที่มี `site_listings` ครบแล้วจะได้รับการ reconcile ในรอบซิงค์ mapping
พร้อม log `Source Zone verified/reconciled: SITE/ZONE via Cross-Seed`
การยืนยันโซนไม่เปลี่ยนภาระ H&R/Quest หรือ manual hold และไม่ใช่ผล recheck ของไฟล์

## ภาระการ seed และ Cleaner

- `required` ระงับการลบเสมอ แม้ผลตรวจจะเก่าแล้ว
- `clear` ใช้ประกอบการพิจารณาลบได้เมื่อผลตรวจ H&R และ Quest ทั้งสองระบบ รวมถึง
  ผลซิงค์ระดับเว็บไซต์ สำเร็จและยังไม่หมดอายุ โดยค่าเริ่มต้นมีอายุ 15 นาที
- ผลตรวจที่ขาดหาย หมดอายุ ล้มเหลว ยังยืนยันไม่ได้ หรือยังไม่รองรับ ถือว่ายังไม่ทราบสถานะ
  จึงใช้แทน `clear` ไม่ได้ หากมีรายการที่ต้องป้องกันแต่ยังหา hash ไม่ได้ ระบบจะระงับ
  การอนุญาตลบ torrent ที่อาจเกี่ยวข้องบนเว็บไซต์นั้น
- `set_manual_hold()` ใช้ตั้งหรือยกเลิกการป้องกันโดยผู้ดูแล แยกจากภาระบนเว็บไซต์
  การยกเลิกการป้องกันนี้จะไม่ยกเลิกภาระ H&R/Quest ที่ยังมีอยู่จริง

เรียก `record_observation()` ได้หลังจากอ่านหน้าที่ล็อกอินแล้ว รู้จักรูปแบบ และ
ยืนยันว่าอ่านครบเท่านั้น หน้า redirect ไปล็อกอิน หน้าปิดปรับปรุง รูปแบบที่ไม่รู้จัก
และรายการที่แบ่งหลายหน้าแต่ยังอ่านไม่ครบ จะใช้ยกเลิกการป้องกันไม่ได้ ปัจจุบันตัวอ่านรองรับหน้า
H&R/Quest ของ BearBit ส่วนเว็บไซต์อื่นต้องพัฒนาและทดสอบตัวอ่านก่อนจึงจะมีผลตรวจ
`clear` ที่ยืนยันใหม่ได้ ดังนั้นค่าเริ่มต้นจะคงการป้องกันงานที่นำเข้าจนกว่าจะมี
หลักฐานเพียงพอ และยังต้องตรวจการใช้ไฟล์ร่วมกันตามเงื่อนไขเดิมก่อนลบด้วย
ผู้ดูแลสามารถเลือก `CLEANER.site_obligations` เป็น `cleaner_policy`
เฉพาะ Dedbit/Bitsuse เพื่อใช้เกณฑ์ ratio/เวลาจาก client สดแทน
โดยไม่แก้สถานะ H&R/Quest ใน ledger และยังคง manual hold กับภาระที่รู้ว่าต้อง seed
ดูรูปแบบ config ใน [NODE_CONFIG.md](NODE_CONFIG.md)

ก่อนเริ่ม Cleaner ทุกรอบ ระบบเรียก `cleaner_obligations.refresh_cleaner_evidence()`
โดยใช้ browser session เดียวสำหรับอ่านภาระและตรวจเพียร์ของงาน Auto Upload
และปิด session เมื่ออ่านเสร็จ
รวมรอบ Cross-Seed เพื่ออ่าน H&R/Seed Quest ของ BearBit โดยไม่ทำ maintenance,
ดาวน์โหลดเนื้อหา หรือเริ่มงานใหม่ ตัวอ่านติดตาม pagination สูงสุด 20 หน้า
และตรวจ identity/login/โครงสร้างทุกหน้า หากหน้าหนึ่งล้มเหลวจะคงการป้องกันไว้
TTL ของหลักฐานยังเป็น 15 นาที ไม่ยืดอายุผลเก่าเพื่ออนุญาตลบ

`reconcile_verified_listings()` เชื่อม listing ที่ `verified=True` และหลักฐาน
จาก Auto Upload เข้ากับ `site_records` โดยตรวจ URL/ID/hash ที่ตรงกัน
ไม่จับคู่จากชื่อ ไม่เขียนทับ hash ที่ขัดแย้ง และไม่ปลด manual hold หรือภาระเดิม
รายการที่สร้างขึ้นยังเป็น `unknown` จนกว่าจะมีผลตรวจเว็บครบถ้วน

เมื่ออ่านหน้าภาระครบและผูก infohash ของรายการที่ต้อง seed ได้ทุกรายการ
จะบันทึก `required_ids`/`required_hashes` ใน `site_sync` เป็นหลักฐาน
`authenticated_complete_site_page_hashes` จึงยืนยัน hash ที่ไม่มีภาระได้
แม้ไม่มี listing ID ของ hash นั้น โดยไม่สร้าง ID สมมติ
ถ้ายังมีรายการที่ต้องป้องกันแต่หา hash ไม่ได้ จะยังไม่อนุญาตวิธีนี้

Cleaner รู้จัก tracker แบบ exact host: `files.bit-sv.net`/`files.bit-sv.cc`
(BearBit), `tracker.cab` (Dedbit), `bitsuse.com`/`www.bitsuse.com` (Bitsuse)
และ `sv-seed.com` (TorrentDD) การรู้จัก host เพียงอย่างเดียวไม่อนุญาตลบ
ต้องผ่านผลตรวจภาระของทุกเว็บที่เกี่ยวข้องด้วย

สวิตช์หลัก `CLEANER.enable` (หรือ `GLOBAL_CLEAN.enable` ใน config เดิม)
และสวิตช์ Cleaner ของ node ใช้กับทั้ง Idle Cleanup และ Smart/Emergency Reclaim
ส่วน reclaim ต้องเปิด `allow_space_reclaim` เพิ่มด้วย
Reclaim ตรวจพื้นที่หลังลบสำเร็จแต่ละงานและหยุดทันทีที่ถึงเป้าหมาย
งานไฟล์ร่วมยังเก็บข้อมูลไว้ตาม guard เดิม และระบบตรวจ references ใหม่หลังหยุดงาน
Cleaner ทำงานผ่าน worker thread เพื่อให้ event loop รับคำสั่งหยุดได้ระหว่างรอบ
เมื่อขอ shutdown จะหยุดก่อนเริ่มลบงานถัดไปและไม่ใช้ inventory ที่อ่านไม่ครบ
ตัวอ่านไฟล์ qBittorrent ส่ง GET พร้อมกันสูงสุด 4 คำขอ โดยแยก HTTP session ของแต่ละ worker
และอ่านรายชื่อ hash/เส้นทางซ้ำเมื่อจบ หากอ่านไม่ครบหรือรายการเปลี่ยนจะไม่อนุญาตลบข้อมูล
หากพบ content root ร่วมกับงานอื่นตั้งแต่ต้น จะเก็บไฟล์ไว้ทันทีและข้ามการอ่านไฟล์ทั้งโหนด
ผลที่ไม่พบ root ร่วมยังต้องตรวจรายการไฟล์สดของทุก client รวมโหนดที่ปิดใช้งานตามเดิม
ไม่มีการเก็บผลอนุญาตลบไว้ข้ามงานหรือข้ามรอบ และยังตรวจ references ใหม่หลังหยุดงาน
log `[Storage Inventory]` แสดงจำนวนงาน จำนวน worker และเวลาอ่านที่สำเร็จ
qBittorrent ใช้ `/torrents/stop` โดย fallback เป็น `/torrents/pause`
เฉพาะเมื่อ endpoint แรกตอบ 404 รองรับผลสำเร็จ 200/204 และก่อนลบ
ต้องอ่านสถานะ `stoppedUP`/`pausedUP` จริง พร้อมตรวจภาระ seed ซ้ำอีกครั้ง

### งานที่เผยแพร่ผ่าน Auto Upload

Cleaner ตรวจเพิ่มสำหรับ infohash ปลายทางที่มีอยู่ใน `upload_jobs` ทุกครั้ง
ทั้ง Idle Cleanup, Smart Reclaim และ Emergency Reclaim:

- หน้าเว็บต้องมียอดโหลดเสร็จ (`Snatched`) อย่างน้อย 1 ครั้ง ไม่ใช้ Hits หรือจำนวนกดดาวน์โหลด
- ต้องยืนยันผู้ปล่อยอื่นอย่างน้อย 1 บัญชีจากตารางเพียร์ที่โหลดเสร็จ 100%
  โดยเทียบกับบัญชีที่ล็อกอินอยู่และไม่นับทุก connection ของบัญชีเรา
- ตรวจ URL/ID ของ listing และ hash ของ canonical torrent ให้ตรงกับงานเดิม
- ผลตรวจมีอายุสูงสุด 5 นาที ตรวจซ้ำก่อนหยุด/ลบ หากหมดอายุหรืออ่านใหม่ล้มเหลวจะเก็บงานไว้

ระบบไม่ลดยอดเพียร์รวมลง 1 แล้วถือว่าเป็นผู้อื่น และไม่นับเพียร์นิรนามที่ยืนยันบัญชีไม่ได้
ตัวอ่าน Dedbit ใช้ `Snatched`/`Peers` จาก listing และตาราง seeders ที่หน้านั้นประกาศ
Bitsuse ที่แสดงเพียงยอดรวมและไม่เปิดรายชื่อเพียร์จะยังไม่ผ่านเงื่อนไขผู้ปล่อยอื่น
เว็บไซต์ที่ยังไม่มีตัวอ่านที่ยืนยันได้จะคงการป้องกันไว้เช่นกัน

ผลตรวจอยู่ใน `retention_check` ของงานและแสดงผ่าน `auto_upload_cli.py show JOB_ID`
เก็บเฉพาะจำนวน สถานะ เวลา และตัวผูกกับงาน ไม่บันทึกชื่อสมาชิก, IP หรือ cookie
การตรวจใหม่จะทำให้ผลเก่าใช้อนุญาตลบไม่ได้จนตรวจเสร็จ
งานที่ไม่ใช่ infohash ปลายทาง Auto Upload ใช้เกณฑ์ Cleaner เดิม
แม้ผ่านสองเงื่อนไขนี้ยังต้องผ่าน ratio/เวลา, H&R/Quest, manual hold และการตรวจไฟล์ร่วมตามเดิม

เมื่อยืนยันว่าลบงานสำเร็จ Cleaner จะบันทึกผลกลับไปยังตำแหน่งของโหนดนั้น โดยเก็บ
ข้อมูล client อื่นและภาระการ seed ไว้ ผลลบงานไม่ใช่หลักฐานว่า H&R หรือ Quest สำเร็จ
ส่วน Cross-Seed ยังคงอ่าน inventory และ manifest จริง พร้อมรับ ID ของรายการ
เว็บไซต์จากฐานกลางประกอบข้อมูลเป้าหมาย การผ่านเงื่อนไข Cross-Seed หรือเพิ่มงานสำเร็จ
จะไม่ยกเลิกภาระการ seed

## การค้นหาชื่อไฟล์ Cross-Seed

`cross_seed_search.py` สร้างคำค้นสำรองให้ BearBit, Bitsuse, Dedbit, TorrentDD และ Unlimitz โดยใช้ตัวอ่าน
ผลลัพธ์และ preflight ชุดเดิม ตัวอย่าง `Other.Mommy.2026.1080p.AMZN.WEB-DL.mkv`
จะลองชื่อเต็มที่ตัดนามสกุลแล้ว ตามด้วย `Other Mommy 2026` และ `Other Mommy`
สำหรับซีรีส์จะคงรหัสตอนหรือซีซัน เช่น `S02E03` ไว้ ส่วนรหัสไฟล์ เช่น `CAD-031`
จะใช้รหัสนั้นเป็นคำค้นสำรอง โดยไม่ตัดเลขภาคออกจากชื่อเรื่อง

ค่าเริ่มต้นลองได้ไม่เกิน 3 คำค้นต่อโซน ปรับด้วย `SETTING.CROSS_SEED_MAX_QUERIES`
ได้ตั้งแต่ 1 ถึง 4 คำ ระบบจะลองคำถัดไปเมื่อยังไม่มี candidate ที่ผ่าน preflight
แม้คำค้นก่อนหน้าจะมีผลลัพธ์ก็ตาม และหยุดคำค้นสำรองในโซนนั้นเมื่อพบ match แล้ว
candidate ID เดิมจะผ่าน preflight เพียงครั้งเดียวต่อแหล่งข้อมูลและโซนในรอบนั้น
หากการตรวจล้มเหลวชั่วคราว ระบบจะมีโอกาสลองใหม่ในรอบสแกนถัดไป

โซนที่ปิดไว้จะไม่ถูกเปิดกลับผ่านค่าเริ่มต้น ตัวกรองหมวดหมู่และค่าค้นหาของแต่ละโซน
ยังถูกส่งผ่าน URL builder โดยมี `search_params` ของเป้าหมายเป็นค่าทับได้
การค้นหาชื่อสั้นอย่าง `Up` รองรับได้ แต่ชื่อเพียงอย่างเดียวไม่ใช่หลักฐานว่าเป็นไฟล์เดียวกัน
ทุก match ยังต้องผ่านการตรวจขนาดและ manifest ตามเงื่อนไขเดิม การเพิ่ม torrent
หรือ tracker ยังคงขึ้นกับค่าที่เปิดใช้งานและการตรวจขั้นถัดไป

BearBit ใช้แบบฟอร์มค้นหา `windows-874` จึงส่งคำค้นด้วย CP874 เพื่อให้ภาษาไทย
กลับมาเป็นข้อความเดิม ตัวกรองโซน/หมวด/searchin/incldead ยังคงเดิม เว็บไซต์อื่นใช้ UTF-8
หากคำค้นมีอักขระที่ CP874 แทนไม่ได้ จะข้ามคำนั้นพร้อม log แทนการตัดอักขระออกแล้วค้นกว้างขึ้น

ผล preflight ส่งต่อ `content_verification`, ขนาดรวมต้นทาง/ปลายทาง และ manifest
ไปยัง audit/execution ครบ โดยสถานะเนื้อหายังคงเป็น `NOT_VERIFIED_RECHECK_REQUIRED`
การจับคู่ชื่อ/ขนาดครบยังไม่ใช่หลักฐานว่า recheck ไฟล์ผ่านแล้ว

พาธไฟล์จาก qBittorrent แบบหลายไฟล์มีชื่อโฟลเดอร์รากนำหน้า เช่น
`Series/sub/E01.mkv` ส่วน manifest ใน `.torrent` แยก root `Series` กับพาธ
`sub/E01.mkv` ระบบตัด root นำหน้าออกเพียงหนึ่งครั้งเมื่อทุกไฟล์มี prefix ตรงกัน
แล้วเทียบโฟลเดอร์ย่อย ชื่อไฟล์ และขนาดอย่างเคร่งครัด
ไม่เปลี่ยนชื่อไฟล์ ไม่ใช้เพียง basename เพื่ออนุญาตเพิ่ม และไม่ยอมรับ path traversal
ขั้นก่อนเพิ่มยังอ่าน source สด ตรวจ root/save path/ความครบ และตรวจ hash ซ้ำบนทุก node ที่เปิดไว้
หาก root prefix ของ client ยืนยันไม่ได้ จะไม่ถือว่าต้นทางเป็นโฟลเดอร์หลายไฟล์

Cross-Seed ที่ hash ใหม่เพิ่มแบบหยุดโดยส่งทั้ง `paused` และ `stopped` สำหรับ API ต่างรุ่น
บังคับ `contentLayout=Original` และไม่ใช้ skip-check/seed mode จากนั้นขอ recheck
รองรับการตอบกลับ recheck แบบ HTTP 200/204 โดยไม่ resume หรือลบไฟล์อัตโนมัติ
API ที่คืน `content_path` ใช้ยืนยันตำแหน่ง root ได้ โดยยังรองรับ `root_path` รุ่นเดิม
ก่อนเพิ่มจะตรวจว่า bytes ของ torrent และ hash ยังตรงกับ manifest ที่ผ่าน preflight

ฟังก์ชัน `run_opt_in_new_hash_cross_seed(..., dry_run=True)` ใช้ทดสอบ gate สด
ถึงจุดก่อนเพิ่ม โดยไม่เรียก add/recheck/resume/delete ส่วน log `Cross-Seed Audit: DRY-RUN ONLY`
บอกเฉพาะขั้น audit หลังจากนั้น execution ยังขึ้นกับ `CROSS_SEED_EXECUTION` ตามปกติ

TorrentDD ใช้ `torrentdd_cross_seed.py` อ่านตารางผลค้นหาและ File List ใน modal
ของหน้ารายละเอียด โดยผูก URL/โซน/ID ก่อนส่งเข้า preflight และ audit เดิม
ไม่เพิ่ม schema ใหม่ อ่านวิธีค้นหาและข้อจำกัด execution ใน
[TORRENTDD_CROSS_SEED.md](TORRENTDD_CROSS_SEED.md)

Unlimitz ใช้ `unlimitz_cross_seed.py` อ่านโซน `browse.php` และ `clip18x.php`
ผูก ID ของผลค้นหากับหน้ายืนยันดาวน์โหลดและ File List ก่อนตรวจ manifest ชุดเดิม
ไม่เปลี่ยน schema ของ mapping ดูตัวกรองและข้อจำกัดใน
[UNLIMITZ_CROSS_SEED.md](UNLIMITZ_CROSS_SEED.md)

## การเพิ่มโปรแกรมบิทชนิดใหม่

`client_registry.ClientRegistry` จับคู่ `type` ใน config กับ `ClientAdapter`
ที่ลงทะเบียนไว้ หากไม่รู้จักชนิดของ client ระบบจะแจ้งข้อผิดพลาด ปัจจุบันรองรับ
`qbit` และ `rtorrent`

ทั้งสองชนิดรองรับการอ่านพื้นที่จาก Swizzin แบบ quota ก่อน แล้วใช้ mount
เมื่อไม่มี quota ตาม [STORAGE.md](STORAGE.md) แหล่งข้อมูลนี้ใช้คำนวณพื้นที่รับงาน
ส่วนการยืนยันไฟล์ร่วมก่อนลบยังตรวจ inventory สดของทุก client ตามเดิม

adapter ต้องกำหนดส่วนต่อไปนี้:

1. factory สำหรับสร้าง client และคลาสที่มีเมธอดตาม `TorrentClient`
2. ตัวอ่าน storage ที่คืนข้อมูลครบในรูปแบบกลาง ประกอบด้วย `hash`, `root` ของเนื้อหา
   แบบ absolute path และชุด `files` แบบ absolute path หากอ่านข้อมูลไม่ครบต้องแจ้งข้อผิดพลาด
3. ตัวอ่านสำหรับอนุญาตลบ ที่คืน inventory สด (`hash`, `progress`, `amount_left`)
   และรายการ tracker (`url`) หากข้อมูลขาดหายต้องระงับการลบ
4. callback สำหรับปิดทรัพยากรของ client หากจำเป็น เพื่อให้ใช้ client ที่ไม่ได้อาศัย
   `requests.Session` ได้
5. `supports_keep_files` ต้องเป็น `false` หาก hook ลบงานของ client หรือเซิร์ฟเวอร์
   ไม่สามารถรับประกันการลบเฉพาะงานโดยเก็บไฟล์ไว้ได้

เมธอดอ่าน inventory ต้องคืนรายการครบถ้วน โดยคืนรายการว่างได้หากไม่มีงาน และคืน
`None` เมื่อเกิดข้อผิดพลาด ส่วนซิงค์ข้อมูลให้ส่ง `client_type`, ชื่อโหนด, path
และวิธียืนยัน `live_client_inventory` โดยหลักฐานเดิมที่ระบุชนิด client จะยังถูกเก็บไว้
ข้อมูลบัญชี client เก็บอยู่ใน config และไม่ถูกคัดลอกลงทะเบียน client ใน mapping

ขั้นตอน Cross-Seed บางส่วนที่เปลี่ยนสถานะหรือเพิ่มงานยังใช้ API เฉพาะของ qBittorrent
การลงทะเบียน adapter อย่างเดียวจึงยังไม่เปิดใช้ขั้นตอนเหล่านั้นกับ client ใหม่
ต้องพัฒนาและทดสอบความสามารถที่เกี่ยวข้องก่อนเปิดใช้งาน การเพิ่ม adapter ยังไม่ถือเป็น
หลักฐานว่าไม่มีงานอื่นใช้ไฟล์ร่วมกัน หรือไม่มีภาระการ seed ค้างอยู่

## การทดสอบ

ตามแนวทางปัจจุบัน ไฟล์ทดสอบเก็บไว้เฉพาะในเครื่องและไม่รวมใน commit รันได้ด้วยคำสั่ง:

```sh
OPENBLAS_NUM_THREADS=2 OMP_NUM_THREADS=2 venv/bin/python -m unittest discover -s tests -v
```

ชุดทดสอบฐานกลางครอบคลุมการย้ายข้อมูล ไฟล์เสียหายและ schema รุ่นใหม่กว่า
อายุหลักฐาน การแยกสถานะ H&R/Quest รายการที่ยังหา hash ไม่ได้ การเขียนจากหลายโปรเซส
การเขียนร่วมกันของ Cross-Seed กับข้อมูลเว็บไซต์ การเรียกตัวอ่านจริงด้วย HTML จำลอง
การบันทึกผลลบงาน และการลงทะเบียน client เพิ่มเติม โดยไม่ส่งแจ้งเตือนหรือเปลี่ยนแปลง
torrent บนเซิร์ฟเวอร์จริง

## คิวอัปโหลดและ variant

เมื่อผู้ใช้ตรวจ My Uploads แล้วว่างานที่ค้าง `publication_uncertain` ไม่ถูกเผยแพร่จริง
คำสั่ง `retry-publication --confirm-not-published` จะตรวจต้นทาง/ฟอร์ม/งานซ้ำใหม่ก่อนปลดงาน
เก็บหลักฐานล่าสุดใน `publication_retry_check` และประวัติการส่งเดิมใน `publication_history`
งานที่ปลดแล้วเป็น `draft`/`prepared` พร้อม `publication_retry.manual_publish_required: true`
คิวอัตโนมัติจะข้ามจนกว่าจะสั่ง `publish` โดยตรง ไม่สูญเสียการป้องกัน source จาก Cleaner
ดูขั้นตอนใน [คู่มือ Auto Upload](AUTO_UPLOAD.md#ยืนยันว่าไม่มีประกาศ-แล้วอนุญาตส่งใหม่)

`upload_jobs` บันทึกสถานะเตรียม/ส่ง/ยืนยัน/recheck ของ BearBit → Dedbit/Bitsuse
และป้องกันไฟล์จาก Cleaner ระหว่างดำเนินการ ส่วน `content_groups` เชื่อม hash
ที่มี payload ตรงกันจาก layout และ piece hashes อ่านวิธีตั้งค่าและความหมายสถานะได้ที่
[AUTO_UPLOAD.md](AUTO_UPLOAD.md) โดยทั้งสองส่วนเพิ่มใน schema 2 แบบคงข้อมูลเดิม

งานอัปโหลดที่ยังกรอกฟอร์มไม่ครบใช้สถานะ `draft` พร้อม `readiness` และ `form_schema`
ส่วน `field_overrides` เก็บค่าที่กำหนดเฉพาะงานโดยไม่เปลี่ยนกฎของงานอื่น
ทั้ง `draft` และ `prepared` จะคงการป้องกันต้นทางจาก Cleaner จนกว่าจะยกเลิกหรือทำงานเสร็จ
